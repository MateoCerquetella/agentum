## Findings

**Blocker:** none.

**Should-fix (non-blocking follow-up):**
1. **`ChatPage.tsx:549` `repoId: filedRepoId ?? ''` degenerate edge.** When a Chat-filed issue has neither `pinnedRepo` nor `workspaceId`, `repoId` is `''`, and the detail page renders the optimistic shell with NO inline error (`GitHubItemDialog.tsx:502` early-returns silently) — a gap in the spec's "hydration failures are visible inline" goal. It is not #237's path and its reachability could not be confirmed from code. Recommend a one-line guard: when `repoPath` is unresolvable but a `workItem` is present, write the same inline error (`GitHubItemDialog` else-branch) instead of a silent shell. **Route to sdd-developer as a follow-up** (or fold into the staging-QA "confirm a Chat-filed issue always carries a resolvable workspace" check). Not blocking because the demonstrated flow always has a workspace.

**Nits:**
1. **Toggle-visibility predicate is a second derivation.** `canScaffoldSpec` (`useComposerState.ts:1646-1648`) computes eligibility inline (`linkedGithubIssueLink?.type === 'issue' && selectedRepoIsGit && !connectionId`) rather than via `deriveIssueSideEffectGate`. This does NOT reintroduce the bug: they agree in the toggle-shown direction (a shown toggle always maps to an eligible gate for the same item), and the submit paths + both callbacks all re-derive with the pure gate and toast on skip. But it means `deriveIssueSideEffectGate` is the single source only for the *execution* decision, not the *render* decision — worth a one-line note (the render gate additionally checks `selectedRepoIsGit`, which the pure gate does not). Documentable, not gating.
2. **`issue-side-effect-gate.ts:4-8` comment says "four places" but lists five** (toggle render + two submit paths + two callbacks). Cosmetic count.
3. **`numeric_comment_id` `rsplit(['-','r'])`** (`gh.rs:546-551`) splits on any `'r'`, which is surprising to read though correct for the documented `#issuecomment-N` / `#discussion_rN` fragments (D3). Low risk — read-only view, negative fallback keeps React keys unique, and it is unit-pinned. Fine as-is.
