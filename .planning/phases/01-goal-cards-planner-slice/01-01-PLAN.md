## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller→Store | Callers (routes / watchdog / CLI shim) cross into the Store with arbitrary `i64` ids + LinkKind values. The Store is the last guard before SQL. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Tampering | Store::add_board_link | mitigate | FOREIGN KEY constraints on board_links (from_card_id, to_card_id) → board_items(id) ON DELETE CASCADE in migration 0015; bind every value via `.bind()`, never format SQL strings (CLAUDE.md sqlx Convention). |
| T-01-02 | Information Disclosure | LinkKind FromStr | accept | LinkKind only knows two variants; unknown strings → ParseLinkKind error. Worst case is a parse error logged as an ApiError downstream (no info leak). |
| T-01-03 | Denial of Service | Store::list_board_links_for_goal (unbounded result) | accept | Per-goal links are bounded by the planner's 3-7 child output per D-04. No N+1 risk; one SELECT scoped to goal_id. Phase 3 will add the larger-graph perf test. |
| T-01-04 | Repudiation | board_links audit trail | accept | `created_at` is captured per row. No update endpoint; only insert/delete. Slice-2 precedent: column rules don't surface updated_at; phase 1 follows. |
| T-01-05 | Tampering | Schema migration replay | mitigate | sqlx::migrate! tracks applied migrations via `_sqlx_migrations` table — 0015 cannot apply twice. Migration is additive + nullable; if 0015 errors mid-run on an existing DB, the partial state (some columns present, some absent) is recoverable by re-running because each statement is idempotent-checking via SQLite's "ALTER TABLE ADD COLUMN" + "CREATE TABLE IF NOT EXISTS"... **caveat:** SQLite's ALTER TABLE ADD COLUMN is not idempotent across reruns. Mitigation: sqlx tracks "migration applied" status so it never re-runs 0015 once recorded. |
