<objective>
Land the CLI shim the planner agent uses as its output surface: `agentum board add-goal` and `agentum board add-card`. Each subcommand is a thin wrapper that resolves the local daemon's URL + bearer token from `~/.config/agentum/profiles.toml` + `credentials.toml`, then POSTs to the right endpoint. The CLI prints the new AG-key on stdout so the planner agent can parse it from its pane scrollback. Unknown `--blocks` keys exit non-zero. Missing credentials exit with a hint.

Purpose: this is the planner agent's ONLY output surface (D-05). The bundled prompt from plan 01-02 names these commands; without this CLI, the planner cannot actually emit cards. Per D-08, the CLI authenticates by reading `credentials.toml` directly — no token in env vars, no token in argv, no token in scrollback.

Output: a new `crates/agentum/src/commands/board/` subdirectory housing the dispatch parent, a thin HTTP client, two subcommand files, plus a small helper added to `terminal/trust.rs` if a usable token-by-url accessor doesn't already exist.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| disk -> CLI | profiles.toml + credentials.toml are user-owned files. CLI reads them; an attacker with shell access can already read these directly so this is not a new attack surface. |
| CLI -> daemon | Bearer token in Authorization header over the profile's URL. Server-side auth middleware (already in place) enforces token validity. |
| CLI argv -> any observer | Process args are world-readable on Linux via /proc/<pid>/cmdline. Tokens MUST NOT appear here. |
| CLI env -> any observer | Some environments leak env vars (e.g. error reports). Tokens MUST NOT appear here. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Information Disclosure | Token in process argv | mitigate | The CLI never accepts a token flag. All token lookup goes through credentials.toml. Grep client.rs + add_*.rs for `arg(.*token|env(.*token` returns zero matches. Verified in Task 1 acceptance criteria. |
| T-05-02 | Information Disclosure | Token in env var | mitigate | The CLI never reads or writes a token env var. Token is loaded into a `reqwest::HeaderValue` with `set_sensitive(true)` so reqwest's tracing layer redacts it from request logs. |
| T-05-03 | Information Disclosure | Token in error messages | mitigate | The catch-all `bail!("daemon returned {status}: {body}")` could in principle echo a token if the daemon ever embedded one in a response. The agentum daemon never does this; treat as accept-with-monitoring (low risk). |
| T-05-04 | Tampering | Symbolic key injection via --key or --blocks | mitigate | `validate_symbolic_key` enforces `[a-zA-Z0-9_-]{1,64}` BEFORE any HTTP call. Server-side `validate_symbolic_key` (plan 01-03) is the second line of defence. |
| T-05-05 | Spoofing | Profile fallback uses a hardcoded token | mitigate | The CLI refuses to run if credentials.toml is missing (exit 4 + hint). No hardcoded fallback. CONTEXT D-08 enforced. |
| T-05-06 | Denial of Service | Planner spams add-card calls | accept | The daemon's rate limiter doesn't currently cover write endpoints (see plan 01-03 threat T-03-05). Local-only solo-developer model; revisit if abuse surfaces. |
| T-05-07 | Tampering | TLS cert validation bypassed when fingerprint pin is set | mitigate | The CLI reuses `crate::commands::terminal::trust::pinned_tls_config(fingerprint)` (trust.rs:298) + `Client::builder().use_preconfigured_tls(cfg)` exactly like the TUI's api.rs:96+175. The rustls config installs a `PinningVerifier` (trust.rs:357) that checks the cert fingerprint against the pinned value on every connection; an MITM presenting a different self-signed cert fails verification. **The CLI MUST NOT call `danger_accept_invalid_certs(true)` — that bypasses the verifier and defeats the pin.** Acceptance criterion below enforces this. |
</threat_model>
