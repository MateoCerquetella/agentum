<objective>
Land the **transactional foundation** for Phase 2 in the `agentum-store` crate plus a regression test in `agentum-core` that pins the `BoardPatch.session_id` double-Option contract. Every later plan reads from this contract.

Purpose: Phase 2 needs two atomic dual-writes — claim (PATCH→doing auto-spawn) and transfer (PATCH `session_id`-rebind/unbind). Both must happen inside a single sqlx transaction so the daemon never leaks a half-bound card or a session row pointing at the wrong card. Phase 1 plan 01-01 already established the sqlx-tx template via `Store::add_board_link`; this plan extends it.

Output: Two new public `Store` methods (`claim_card`, `transfer_card_binding`), unit tests proving both transactional shapes plus conflict-on-already-bound, and a serde regression test in `agentum-core` confirming `BoardPatch.session_id` already distinguishes omitted vs explicit-null vs explicit-value (the field exists from Phase 1; this plan locks the test). Task 3 also adds a const-eval static-assert pinning `BoardPatch: Clone` so plan 02-03 can rely on the trait without a conditional fallback (per plan-checker iter-1 W-4).
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→store | New `Store::claim_card` and `Store::transfer_card_binding` mutate session and board_items rows. Called from the auth-gated PATCH handler in plan 03; no direct client reach. |
| store→DB | All mutations inside a `tx` from `self.pool.begin()` — atomic per SQLite-WAL transaction semantics. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Tampering | Cross-card session theft via concurrent PATCH races | mitigate | The new sessions row is created INSIDE the same tx that sets the card's session_id; SQLite serialises writes via WAL — no interleave window. |
| T-02-02 | Repudiation | Half-bound state on partial failure | mitigate | Transactional rollback on any step failure. Tests 2 and 4 (claim_card) and tests 3 and 5 (transfer_card_binding) prove rollback explicitly. |
| T-02-03 | Information disclosure | Conflict error message leaks session/card ids | accept | Error message contains card_id and session_id (low-sensitivity; both are internal opaque ids exposed via `/api/board` and `/api/sessions` to the same authenticated user). |
| T-02-04 | Denial of service | Long-running transaction blocks other writes | accept | SQLite-WAL allows readers to proceed during a writer transaction; this transaction is bounded (3 SELECTs + 3 UPDATEs + 1 INSERT, all single-row by PK) — sub-millisecond typical. |
| T-02-SC | Tampering | No new package installs in this plan | n/a | Plan modifies in-repo crates only; no Cargo.toml additions; no slopcheck needed. |
</threat_model>
